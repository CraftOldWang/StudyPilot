# 这轮开发为何过慢，以及 RAG 结果如何解释

2026-09-09，用户暂停 Goal 后的只读复盘。统计边界截至用户要求暂停的消息，后续审计不混入开发消耗。已停止两个批量学习 Python 执行器；后端已发出的回合全部终结，没有新建实验。本文不批准恢复执行。

## 结论

主要问题是我把“做出可演示核心链路并取得几组可信数据”组织成了一个串行、跨六个里程碑、验收和归档都很重的长任务。真实环境故障和模型不稳定存在，但不足以解释全部耗时。用户目标不是不可理解；目标落到规模控制、优先级和停止条件上时，我没有做得足够好。

也没有证据支持“整个代码库没有抽象，只能反复通读”。现有业务边界可辨识，最大生产 Java 文件338行；问题更多是大量小步骤放进一个持续膨胀的会话、反复切换模块和验收层次，以及当前设计入口不够清楚。

## 对用户提出的原因逐项回答

1. **目标模糊：不是主要原因。** 课件入库、重点规划、学习闭环、三个指标的方向清楚。我把这些方向进一步扩成六组切块、100题、320次回答/评审、18个五点学习会话、多种故障注入和多套版本归档，缺少一个与你的面试/演示价值匹配的总成本预算。
2. **任务范围确实广，但应该分开交付。** 这轮不只是RAG或一个Agent：还改原生multipart、对象存储合并、异步恢复、前端、Anki、ASR以及评测工具。23次提交证明做了实质工作；然而不该等整包验收齐备才给你一个容易掌握的完成版本。
3. **测试不是没用，顺序和规模有问题。** 找到了真实死锁、索引部分失败、重复上传、ASR缓存恢复等问题。但大量本地结构测试通过后，真实模型仍连续用错选项格式、遗漏未解决问题、引用本轮未读来源。说明这些测试没有覆盖决定产品能否演示的模型交互。应先用一条真实小链路解决这些问题，再运行大矩阵，而不是把正式对照当成调试器。
4. **哈希和冻结本身不是错误，使用过重。** 文件去重、阶段结果复用需要内容指纹，防止实验中混用参数也合理。但多个版本目录、独立manifest、失败归档、原始JAR、摘要与重启观察记录一起成为了日常推进条件。前两轮正式尝试共107次调用，却没有完整会话；期间同一性质的重启恢复又被重复验证。保留失败即可，不必每次把整套正式协议从头搬一遍。
5. **长上下文与重复确认是主要放大器。** 单次输入中位数14.5万、13次压缩；PROGRESS读23次、目标计划读15次、PlanningService读11次。缓存缓解输入成本，但不消除模型时延、上下文定位和反复恢复工作状态。不能把全部重复读取算浪费，但这种串行主会话明显过长。
6. **提交有做，但粒度并非一直足够小。** 不能说15小时没commit；也不能把23次commit当成已经控制好改动面。部分宽提交混合实现、脚本和证据，用户难以逐步理解。
7. **代码不是零抽象，但有维护负担。** 当前tracked生产Java 202文件/11,011行，后端测试80文件/6,793行，脚本42文件/3,871行，Markdown文档64文件/3,594行。行数包含空行/注释；不是复杂度评分。为一个演示项目，支持性代码和材料占比确实偏大。可见的具体问题是旧直接规划入口仍在、若干阶段依赖字符串和JSON、设计文档仍混有M0–M2旧叙述。不能据此宣判全库质量，但应该收敛入口。

我不为这些因素编造百分比分摊。可量化的是调用、重复、耗时区间、提交和实际失败；“哪一项占了几小时”需要更细的运行计时，现有日志不能完全分离模型推理、调度、人工暂停与后台执行。

## 为什么 RRF 与父块没有总体提升

先分开问题：**RRF改变排名，父块回填改变送给模型的上下文。它们都不是天然优于基线的开关。**

| 60道可回答题 | BM25 | 向量 | RRF |
|---|---:|---:|---:|
| 标注证据Hit@5 | 42/60 | 55/60 | 55/60 |
| MRR@10 | 0.6068 | 0.7500 | 0.7214 |

逐题重算：RRF相对向量只救回1题（进程切换时上下文保存/恢复），也丢掉1题（最小化最大延迟中的截止时间排序）；另4题两者都没命中。不是“完全没有作用”，而是本组互补收益与干扰抵消。见`docs/evidence/final/rag-paired-diagnosis.json`。

当前RRF实现给BM25与向量相同权重，分数为两路`1/(60+rank)`之和，不理解某一路是否可靠。中文问题配英文算法课件时，BM25明显较弱；代码使用`content`字段的standard analyzer，没有翻译或查询改写。弱路仍有同等投票权，可能把向量路较好的结果挤下去。这个机制解释与分课程结果相符，但尚未逐一证明每个排名损失的因果。

向量在这个集合里确实很强，但语料也很小：18个原件只有137个child，而且检索还按课程知识库过滤；多数题是来源片段可直接回答的课件问题。不能据此推断真实复杂课程中向量总是足够。

父块：同一子块排名、4096正文预算下，子块证据覆盖55/60，父块54/60；算法18→14，OS19→20，编译原理18→20。800的child经常已经包含足够答案；原始全库中56/60的标准证据本就能装进某个child。扩到最大2400的parent，预算4096往往容纳不了两个大parent；当前实现整块放入、放不下就跳过，可能丢掉更低排名的有效来源。父块的“补足上下文”与“挤占其它证据”在本组发生了真实取舍。

**测试集有局限，但不能因为没有提升就换到能涨分的集合。** 这份集合由模型起草、Codex复核，并非真实学生独立提问；主要偏局部事实和定义，未系统分层覆盖跨段解释、跨章节比较、稀有术语/符号、相似概念干扰、多来源推导。只认可一个完整原文摘录的标签也会漏掉等价证据。模型自动评审还出现了漏判，不能把自动分数当人工准确率。

再次讨论后，值得做的是从真实使用方式补一小组有明确类别的问题，先看每类失败，而不是继续扩大随机题量或预设父块/RRF必须涨分。现有结果保留；暂不新增评测调用，也不调整检索算法。

## 建议的新工作方式，等待讨论后再执行

- 先交付并讲清一个“课件→计划→讲解→五题→三卡→恢复”的桌面演示版本，当时的架构讨论稿现已由 [当前技术设计](../design/StudyAgent-技术设计方案.md) 取代。
- 下一步只选一个问题和明确改动边界。按模块小步提交；每个修复只跑相关测试，再跑一次真实回归。
- 真实模型开发烟测和最终指标实验分开：先用小样本暴露格式、引用和状态问题；验证稳定后再确定是否值得做三重复/多课程。
- 每轮设时间与调用上限，到点给出可审阅结果和未决问题，重新决定方向；不让“持续完成Goal”变成无止境加验收。
- 实验记录保留运行参数、输入数据、原始结果和一个汇总脚本即可；只在比较结果确有需要时记录版本，不逐项增加冻结与哈希证明。
- 当前不重构、不续跑18会话、不新增reranker，不以改善指标为理由重写测试集。先由你掌握系统和决定下一步。
